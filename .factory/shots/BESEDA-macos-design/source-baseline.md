# Current source surface baseline (not a screen capture)

Source inspected in BESEDA-310; dimensions below are **SwiftUI constraints in points**, not measured pixels or observed window bounds. No app or window was launched. Minimum macOS is 14.2 ([Package.swift](../../../Package.swift)); the native menu-bar decision specifies `MenuBarExtra` and system controls ([decision](../../../docs/decisions/native-menubar-app.md)). English coverage is source-only, not a verified English-system appearance ([buyer gate](../../../docs/decisions/english-first-buyers.md)). Apple's [macOS windows HIG](https://developer.apple.com/design/human-interface-guidelines/windows) was reachable by HTTP; native window/toolbar behavior remains system-owned, not a fixed mockup.

## Geometry and appearance

- Menu-bar entry uses `MenuBarExtra` with `.window` style; label is a state-dependent symbol and optional text ([BesedaApp.swift:33–86](../../../Sources/Beseda/App/BesedaApp.swift)). Popover content is **340 pt wide**, 14 pt inset, vertical gap 12; height is content-dependent, with no fixed point height ([MenuBarPopover.swift:11–29](../../../Sources/Beseda/App/Views/MenuBarPopover.swift)). Live transcript scroll area is 88 pt tall when lines exist; meter labels reserve 66 pt and icons 14 pt ([MenuBarPopover.swift:230–291](../../../Sources/Beseda/App/Views/MenuBarPopover.swift)). System `headline`, `subheadline`, captions, native buttons/switch, semantic primary/secondary/tertiary and accent colors; warning orange, error/stop red, readiness green. Hovered rows use primary at 6% opacity ([MenuBarPopover.swift:68–111, 161–215, 365–425](../../../Sources/Beseda/App/Views/MenuBarPopover.swift)). Popover focus/key behavior and final shadow/material depend on macOS and were not observed.
- Archive is a SwiftUI `Window` with **default 1100 × 720 pt**, not an enforced size ([BesedaApp.swift:17–31](../../../Sources/Beseda/App/BesedaApp.swift)); content minimum **880 × 560 pt**. `NavigationSplitView` sidebar min/ideal/max **240/300/420 pt**, searchable in sidebar, toolbar primary actions ([ConversationsWindow.swift:7–52](../../../Sources/Beseda/App/Views/ConversationsWindow.swift)). Actual titlebar height, split divider, toolbar collapse, window frame and appearance remain unknown. Detail header/content horizontal inset 24 pt, header top 20 pt; scroll content top/bottom 18/24 pt, column gap 18; transcript/result content max 680 pt, info max 620 pt ([CallDetailView.swift:33–74, 100–138, 443–471, 608–638](../../../Sources/Beseda/App/Views/CallDetailView.swift)). Bottom player uses `.bar` background and 24/12 pt horizontal/vertical inset ([PlayerBar.swift:71–116](../../../Sources/Beseda/App/Views/PlayerBar.swift)). Native sidebar list selection, segmented picker, toolbar, divider and light/dark semantic styles follow system appearance, not hard-coded colors.

## Actual conditional order / behavior

1. Popover top: optional speech-model download progress and optional diarizer prefetch spinner, then status icon/title/subtitle, recording timer if recording, optional job progress and recording warning ([MenuBarPopover.swift:11–62, 69–154](../../../Sources/Beseda/App/Views/MenuBarPopover.swift)). Idle/completed shows microphone-denied or missing-model warning before ready icon; subtitle reports denied mic, missing model Settings route, or auto-detect state. Working shows stage and caption; failed shows failure message; completed with a ready recent call says transcript ready ([MenuBarPopover.swift:114–161](../../../Sources/Beseda/App/Views/MenuBarPopover.swift)). Only microphone permission is read without side effects; system audio isn't known until a tap opens ([MenuBarPopover.swift:163–169](../../../Sources/Beseda/App/Views/MenuBarPopover.swift)).
2. Recording replaces the lower recent-call and command sections: **Pause/Resume → Stop** (red prominent, ⌘R), microphone and other-person level meters, optional collapsed live key-points/draft disclosure. Paused state says audio is not written; live lines show the last eight lines and scroll to newest ([MenuBarPopover.swift:172–270](../../../Sources/Beseda/App/Views/MenuBarPopover.swift)). There is no recording-time archive/Settings/Quit section in this popover. `isRecording` and busy status are controller state, not inferred from a picture ([AppController.swift:16–32, 193–210](../../../Sources/Beseda/App/AppController.swift)).
3. Not recording (idle, working, failed, completed): **Start recording** (⌘R; disabled while busy or speech model missing) → **Auto-record switch**. Working additionally says the saved call can finish processing in background. Divider → last-ready-call card (title, app, duration, optional preview, Open and Copy transcript) OR three recent rows OR empty text → divider → Conversations, Settings (⌘,), Quit (⌘Q) ([MenuBarPopover.swift:199–226, 295–369](../../../Sources/Beseda/App/Views/MenuBarPopover.swift)). A missing model does not remove the auto-record switch or commands; it disables manual Start and points to Settings → Processing ([MenuBarPopover.swift:126–159, 199–215](../../../Sources/Beseda/App/Views/MenuBarPopover.swift)). Actual rendered localization, popover clipping and keyboard focus order are unverified.
4. Archive sidebar: optional upcoming calendar events, optional live recording row, empty/search state or calls grouped by day, optional Show more, storage footer. Rows show title and clock/duration/app for ready calls or clock/status for failed/in-progress calls; processing row shows stage/progress ([CallSidebar.swift:13–81, 88–210](../../../Sources/Beseda/App/Views/CallSidebar.swift)). Toolbar conditionally offers event link, webhook send/history, copy format, delete (with confirmation), then record/stop; record disabled while busy ([ConversationsWindow.swift:22–66, 101–146](../../../Sources/Beseda/App/Views/ConversationsWindow.swift)).
5. Selected detail: title, date/app/channel(s)/optional call type, segmented **Transcript / Results / Info**; optional processing/failure banner and previous-call block precede tab content; player stays below scroll area ([CallDetailView.swift:4–137](../../../Sources/Beseda/App/Views/CallDetailView.swift)). Processed calls with result open Results; failed open Info; other calls open Transcript. A result arriving while selected switches to Results ([CallDetailView.swift:76–99](../../../Sources/Beseda/App/Views/CallDetailView.swift)). Transcript has selectable text, speaker grouping, seek timestamps, rename/merge actions; Results has call-type rerun menu, copy result if present, and generate/running/error/ready states, including regeneration retaining prior text ([CallDetailView.swift:141–170, 438–607](../../../Sources/Beseda/App/Views/CallDetailView.swift); [CallSummaryView.swift:14–159](../../../Sources/Beseda/App/Views/CallSummaryView.swift)). Info fields: Recorded, Channels, Duration, State, optional Calendar event, optional Speed/Model, Service delivery, Folder, optional Error, expandable technical `session.json` log ([CallDetailView.swift:608–691](../../../Sources/Beseda/App/Views/CallDetailView.swift)). Player has play/pause, slider with speaker strip/legend, time and speed when audio exists; retained-audio absence disables play and shows storage route ([PlayerBar.swift:71–193](../../../Sources/Beseda/App/Views/PlayerBar.swift)). No inspector pane is currently present.

## Safe concept rendering route

In a **separate non-product Swift executable/script in this shots directory**, define pure SwiftUI concept views with synthetic strings and explicit light/dark environment and fixed proposed point sizes (340 pt menu; 1100 × 720 pt archive). On the main actor, render each via `ImageRenderer(content: concept.environment(\.colorScheme, .light))`, set `renderer.scale = 2`, obtain `nsImage`, and write its bitmap TIFF representation as PNG through `NSBitmapImageRep.representation(using: .png, properties: [:])`. Repeat for dark. Do not instantiate `BesedaApp`/`AppController`, order an `NSWindow`, use screen capture, request permissions, open audio or alter shipping view paths. ImageRenderer may not reproduce native menu-bar chrome, toolbar, search field or vibrancy outside a window: annotate these as concept approximations, not real app captures; validate renderer output and pixel bounds before using it as visual evidence.
