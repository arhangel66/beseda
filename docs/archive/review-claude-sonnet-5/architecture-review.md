# Podushka — архитектурный обзор и находки по багам

Автор: Claude Sonnet 5 (Claude Code). Ревью read-only, код не менялся.
Метод: чтение ключевых документов (README, AGENT.md, MVP_PHASE_PLAN.md, implementation_journal.md,
Package.swift) + пять параллельных агентов, каждый разобрал один слой кода (App/, Audio/,
Transcription+Summarization+Storage+Calendar/, python/, и отдельно UX — см. `ux-review.md`).

Общее впечатление: для PoC качество кода выше среднего — нет форс-анврапов в App/, SQL
параметризован и не течёт по statement'ам, потоковая модель в App/ в целом аккуратная
(`@MainActor`/`@Observable`, `[weak self]`). Основные риски сосредоточены в четырёх местах:
границе реального времени в Audio/, отсутствии таймаутов на границе Swift↔Python,
несвязанности storage-уборщика со статусом звонка, и в python-воркере, который может упасть
целиком от одной кривой строки на stdin.

## Топ-5 находок (must fix)

### 1. [HIGH] Нет таймаута на диалог с ASR-воркером — зависание может быть бесконечным и молчаливым
`Transcription/ASRClient.swift:88-112, 228-270`

`transcribe()` резолвит continuation только по `job_done`/`job_failed`/завершению процесса.
Таймаута нет. Если воркер завис в инференсе (не упал, просто не отвечает), `await
asrClient.transcribe(...)` не вернётся никогда — звонок навсегда останется в `.transcribing`
без всякой обратной связи пользователю.

Хуже: если `job_done` пришёл, но не распарсился, `handleLine` просто логирует ошибку
(`"Invalid ASR response..."`), а `pendingJobs[id]` продолжение **не резолвится вообще** —
это не медленный путь, а тихий вечный хэнг.

Согласуется с находкой в python-воркере (#5 ниже): у воркера тоже нет таймаута на свою сторону
операции, так что зависание может начаться на любом конце.

**Рекомендация:** добавить дедлайн на `transcribe()` (например, `Task.sleep` гонка с ожиданием
continuation), по истечении — резолвить как `job_failed` с понятной причиной и разрешить
Retry. Также резолвить continuation как failure и в ветке "не удалось распарсить job_done".

### 2. [HIGH] Уборщик хранилища не знает о статусе звонка — Retry может стать тупиком
`Storage/StorageJanitor.swift:54-59, 90-106` + `App/AppController.swift:212-223, 1562-1568`

`RetentionRule.immediately.maximumAge == 0` → `isExpired` истинно для любого файла сразу же
(`App/AppSettings.swift:29-32`). `AppController` при старте вызывает `failInterruptedCalls()`
(помечает прерванный аварийным завершением звонок как `failed`, `canRetry == true`), и сразу
следом — `startDailySweep()`, синхронно на том же запуске.

Уборщик обходит папку звонков по суффиксу имени файла и mtime — он ничего не знает про
`calls.status`. При настройке хранения "Сразу" сценарий воспроизводится буквально:

1. Приложение падает во время транскрибации.
2. Пользователь перезапускает приложение.
3. Звонок помечен `failed`, кнопка "Повторить" видна.
4. Uборщик уже стёр `me.raw.wav`/`them.raw.wav` на этом же запуске.
5. Нажатие "Повторить" → файл не найден.

Это не гипотетический edge case, а прямое следствие порядка вызовов в `AppController.init`.
Более широкий вариант той же причины: дневной таймер-уборщик в принципе может стереть файл,
который в этот момент читает активная транскрипция другого/этого звонка (нет lock/"файл
используется" проверки) — см. также находку #2 в Audio (аудиопоток и уборка не синхронизированы).

**Проверено:** `Tests/PodushkaTests/StorageJanitorTests.swift` не содержит ни одного упоминания
`retry`/`status`/`failed` — этот путь сейчас никак не покрыт тестами.

**Рекомендация:** уборщик должен либо получать список "живых" (не полностью завершённых/retry-able)
call ID от `CallStore` и исключать их файлы из свипа, либо `failInterruptedCalls` должен
исполняться (и, если применимо, ретраить) **до** первого запуска уборщика, а не в соседней
строке до него.

### 3. [HIGH] Нарушение real-time аудио-потока в захвате микрофона
`Audio/MicrophoneCapture.swift:56-62`, `Audio/PCMFloatRecorder.swift:59-71`

Колбэк `AVAudioEngine`-тапа (по документации Apple выполняется на realtime render thread)
напрямую вызывает `recorder.append(pcmBuffer:)`. Внутри `PCMFloatRecorder` на этом же потоке
аллоцируется новый `[Float]`, берётся `NSLock`, и `append` к растущему массиву `samples`
может вызвать реаллокацию/копирование — всё это на аудио-потоке. Тот же `NSLock` берётся и с
UI/главного потока при чтении уровня для индикатора. Под нагрузкой или при конкуренции за
лок render-колбэк может не уложиться в дедлайн → слышимые щелчки/пропуски, в худшем случае —
watchdog-крэш; риск растёт с длительностью звонка (массив только растёт).

**Рекомендация:** на аудио-потоке — только копирование сырых сэмплов в предварительно
выделенный lock-free буфер (кольцевой буфер / `TPCircularBuffer`-подобная схема); всё
аллоцирующее и блокирующее (лок, запись в файл, рост массива) — на выделенном фоновом потоке,
которому render-колбэк просто сигналит.

### 4. [HIGH] Нет выравнивания часов между двумя каналами захвата
`Audio/DualCapture.swift:126-128`, `Audio/SystemAudioTap.swift:72`, `Audio/CallPlayer.swift:94`

`systemTap.start()` запускается синхронно, затем `await microphone.start()` — а это ожидает
асинхронную проверку разрешения на микрофон и раскрутку `AVAudioEngine`. Общего сигнала старта
или посэмпловых меток времени нет, поэтому нулевой фрейм `them.raw.wav` не соответствует
тому же моменту времени, что нулевой фрейм `me.raw.wav` — любая задержка на permission-prompt
или медленный старт движка становится фиксированным сдвигом, запечённым в запись с самого начала.
`kAudioSubTapDriftCompensationKey` компенсирует дрейф тапа относительно **агрегатного устройства**,
но не относительно независимо тактируемого `AVAudioEngine`-микрофона.

MVP_PHASE_PLAN.md называет это "Medium"-риском ("может дрейфовать на длинных звонках"), но по
факту рассинхрон присутствует с нулевой секунды, а не только накапливается — и напрямую бьёт
по выравниванию двухканального ASR и по синхронному плееру (`CallPlayer.swift:94` полагается на
общий момент старта).

**Рекомендация:** зафиксировать единый host-time старт для обоих каналов (например, начать оба
захвата, но буферизовать/обрезать до общей точки старта по `AVAudioTime`/host time, а не по
порядку вызовов `await`), и как минимум логировать фактический сдвиг в `session.json` для
диагностики уже записанных звонков.

### 5. [HIGH] Python-воркер падает целиком от одной синтаксически валидной, но не-словарной JSON-строки
`python/asr_worker.py:262-267` (`run_jsonl`), `:215` (`handle_job`)

`run_jsonl` ловит только `json.JSONDecodeError`. Если строка распарсилась в `[1,2]`, `null`
или `42` (валидный JSON, не объект), `handle_job` тут же вызывает `job.get("type")` →
`AttributeError` без окружающего `try` → процесс падает целиком. Это не "текущая задача
упала", а "воркер больше не отвечает ни на одну будущую задачу" — вплоть до перезапуска
Swift-стороной.

Рядом: `run_jsonl:253` вызывает `load_model()` до старта цикла и вне `try/except` — сетевой сбой,
неверный model id или битый HF-кэш приведёт к падению до отправки события `ready`; Swift увидит
только закрытый pipe, а не структурированный `job_failed`.

**Рекомендация:** обернуть тело цикла `run_jsonl` в `try/except Exception`, при любой ошибке
(включая не-dict JSON) эмитить `job_failed`/диагностику в stderr и продолжать читать stdin,
а не давать исключению всплыть до `main`. `load_model()` также обернуть и эмитить структурированное
событие ошибки загрузки модели вместо голого traceback + exit.

## Остальные находки (по слоям, без топ-5, среднего/низкого приоритета)

### App/ (AppController и вокруг)
- **[MED]** `runRetry` (`AppController.swift:902-1135`) — почти дословный дубликат
  `runDualRecording` (661-900), уже разошёлся: retry пропускает `AudioNormalizer.normalize`
  и предполагает, что `*.asr.wav` уже существует. Будущие изменения основного пайплайна нужно
  будет вручную повторять здесь же — источник расхождений.
- **[MED]** `writeLogLine` (`AppController.swift:1591-1610`) — синхронный небуферизованный
  I/O (открыть/seek/записать/закрыть) на каждый вызов `appendLog`, на `@MainActor`, а вызывается
  из потенциально частого `diagnosticsHandler`/`progressHandler`. Может подвешивать UI при
  многословном воркере.
- **[MED]** `restartWorker()` (`AppController.swift:548-555`) вызывает `asrClient.stop()`
  безусловно, даже при `status.isBusy` (guard защищает только присвоение `status`). Сейчас
  метод не вызывается ни из одного View (мёртвая точка входа), но это ловушка для будущей кнопки
  "Перезапустить воркер" в настройках.
- **[MED]** `activeTask` (`AppController.swift:132/243/632`) присваивается, но никогда не
  читается/отменяется/ожидается. `quit()` не дожидается его перед `NSApplication.terminate` —
  можно оборвать запись `me.raw.wav`/метаданных сессии на выходе из приложения.
- **[MED]** `observeAutoDetectSettings()` (`AppController.swift:525-536`) — переустановка
  `withObservationTracking` из `Task{@MainActor}`, запланированного `onChange`; в окне между
  срабатыванием и переустановкой есть шанс потерять быстрое двойное изменение настройки.
- **[LOW-MED]** `ProjectPaths.swift:9` — `projectRoot` вычисляется от `#filePath` (путь на
  машине сборки), fallback — `cwd`. Ломается для любой распространяемой сборки (GUI-приложение
  из Finder имеет `cwd` вроде `/`), тихо уводя все пути (calls dir, sqlite, лог, ASR-воркер) не
  туда. `PODUSHKA_ROOT` спасает только явные запуски.

### Audio/
- **[MED]** `CallRecordingPolicy.swift:61-66` — при ручной остановке звонка `finishedHolder`
  не выставляется (ручные записи никогда не идут через ветку `.start` в `update()`), поэтому
  guard "тот же звонок — не перезапускать" (строка 40) не срабатывает. После
  `minimumGapBetweenRecordings` (60с) `CallDetector` тихо начинает новую запись того же
  ещё идущего звонка, который пользователь сознательно остановил — прямое противоречие

  **Проверено:** `Tests/PodushkaTests/CallRecordingPolicyTests.swift` тестирует много
  комбинаций `manualRecordingActive`, но не сценарий "ручная запись закончилась → авто-детект
  того же holder'а после паузы" — этот путь не покрыт.
- **[MED]** `AudioNormalizer.swift:32-34` — бросает исключение при любом непустом stderr от
  ffmpeg, даже после подтверждённого exit code 0; нет проверки, что выходной файл реально
  создан и не пуст.
- **[LOW-MED]** Нет обработчика краша/принудительного завершения для разрушения агрегатного
  устройства/тапа (весь teardown — только через явные `defer`/`catch`); при `SIGKILL` во время

## Пробелы в тестах (сводка)

Swift-сторона: тестовый набор в `Tests/PodushkaTests/` неплохо покрывает чистую логику
(`CallRecordingPolicyTests`, `TranscriptMergerTests`, `StorageJanitorTests`,
`SpeakerAssignmentTests` и др. — 15 файлов), но **конкретно не покрывает ни одну из найденных
здесь проблем**:
- `CallRecordingPolicyTests` — нет теста на "ручная остановка → авто-рестарт того же звонка".
- `StorageJanitorTests` — нет теста на связку "статус звонка = failed/retry-able" → "файл не
  должен быть сметён".
- `TranscriptMergerTests` — нет теста на перекрывающиеся по времени сегменты двух каналов.
- Нет теста на `ASRClient.transcribe()` без ответа/с невалидным `job_done` (проверка, что
  continuation вообще резолвится).

Python-сторона (`python/tests/test_asr_worker.py`): покрыт только happy path чистых функций
(`tokens_to_words`, прогресс `transcribe()` через `FakeModel`, один тест на
`job_started→job_progress→job_progress→job_done`). **Полностью отсутствуют тесты на:**
- сам цикл `run_jsonl` (парсинг построчного JSONL, восстановление после невалидной строки,
  порядок события `ready`, и главное — крэш на не-словарном валидном JSON, находка #5);
- любой путь `job_failed` (отсутствующий `audio_path`, неподдерживаемый `type`, исключение
  внутри `transcribe`, сбой загрузки модели);
- `ping`, `sentence_to_segment` (дефолт/округление уверенности, фильтрация пустого текста);
- `probe_duration_sec`/`normalize_audio`/`require_file`/разбор CLI-аргументов (`main`,
  `--self-test`, `--normalize-only`) — все они шеллятся в `ffmpeg`/`ffprobe` и не тестируются
  автоматически, только вручную (см. `docs/asr-bakeoff.md`).

**Рекомендация по приоритету новых тестов** (наибольшая отдача за наименьшее усилие):
1. Регрессионный тест на находку #5 (python) — не-dict JSON на stdin не должен убивать воркер.
2. Регрессионный тест на находку #2 (janitor/retry race) — файл, принадлежащий `failed`/
   `retryable` звонку, не должен быть сметён сразу после `failInterruptedCalls`.
3. Регрессионный тест на находку в `CallRecordingPolicy` (ручная остановка → не рестартовать).
4. Тест на `ASRClient.transcribe()` без ответа / с битым `job_done` — continuation должен
   резолвиться как ошибка, а не висеть вечно.
