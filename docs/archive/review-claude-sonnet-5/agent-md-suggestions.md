# Предложения по дополнению AGENT.md

Автор: Claude Sonnet 5. Текущий `AGENT.md` в корне — хорошая, компактная точка входа
(технологический стек, data flow, ключевые файлы). Ниже — то, чего мне при чтении/аудите
проекта не хватало и что заняло время на самостоятельное выяснение; предлагаю добавить как
короткие разделы, не переписывая существующий файл целиком.

## 1. Команды сборки и тестов (сейчас есть только сборка приложения)

В `AGENT.md` есть команда сборки (`./scripts/build_podushka_app.sh`) и self-test ASR-воркера,
но нет команд запуска тестов, хотя тестовые наборы есть и довольно большие:

```bash
# Swift-тесты (15 файлов в Tests/PodushkaTests/)
swift test --package-path .

# Python-тесты ASR-воркера
cd python && uv run pytest
```

## 2. Модель многопоточности — где можно писать код, а где нельзя

Явно зафиксировать инвариант, который сейчас нигде не написан текстом, а выводится только
из чтения кода:
- `AppController` — `@MainActor`/`@Observable`, сюда безопасно добавлять код, полагаясь на
  главный поток.
- Колбэки `AVAudioEngine`-тапов и Core Audio process tap'ов (`Audio/MicrophoneCapture.swift`,
  `Audio/SystemAudioTap.swift`, `Audio/PCMFloatRecorder.swift`) выполняются на realtime
  render-потоке — там **запрещены** аллокации, локи, файловый I/O. Любое изменение в этих
  файлах должно сохранять "просто скопировать сэмплы и уйти" на этом пути.
- Python-воркер (`python/asr_worker.py`) обрабатывает задачи строго последовательно,
  один процесс на весь пайплайн — при добавлении новой логики помнить, что зависшая задача
  блокирует вообще всё, таймаута нет.

## 3. stdout python-воркера — жёсткое правило

Стоит вынести в отдельную заметную строку (сейчас это подразумевается протоколом, но нигде
явно не запрещено): **в `python/asr_worker.py` и всех его зависимостях stdout зарезервирован
только под JSONL-протокол**. Любой `print()`, случайный лог сторонней библиотеки в stdout или
непойманное исключение с traceback в stdout ломает парсер на Swift-стороне. Диагностика — только
через `log()` (stderr).

## 4. docs/ — что из этого уже сделано, а что предложение

В `docs/` лежат 13 файлов вперемешку: одни описывают уже принятые и реализованные решения
(`capture-spike.md`, `asr-bakeoff.md` — прошедшие эксперименты; `ui-redesign-plan.md` и
`ui-redesign-v2-plan.md` — я проверил, эти оба реализованы почти полностью), другие —
незавершённые/предлагаемые направления (`speaker-diarization-plan.md`,
`summarization-local-model-plan.md`, `auto-start-plan.md`). Агенту, впервые открывающему
проект, стоит явно сказать: **не считайте файл в `docs/` описанием текущего состояния, пока не
сверили с кодом** — статус каждого плана стоит проверять по факту, а не по названию файла.

## 5. Саммаризация — сейчас это заглушка, не настоящая модель

`implementation_journal.md` фиксирует, что саммаризация в Phase 1 (данные и ядро), но это
не сразу очевидно из `AGENT.md`. Стоит явно отметить: **`SummarizationProvider`, который сейчас
подключён к UI (`CallSummaryView`), — это `MockSummarizationProvider`, возвращающий заглушечный
текст, не связанный с реальным содержанием звонка.** Агент, которому попросят "поправить баг в
саммари", должен сразу понимать, что "баг" может быть в том, что это вообще не настоящая
саммаризация, а не в логике конкретного бага.

## 6. Известная связка "уборщик хранилища ↔ статус звонка" — не трогать вслепую

Стоит одной строкой предупредить будущих агентов (в том числе как ссылка на
`docs/review-claude-sonnet-5/architecture-review.md`, находка #2): `Storage/StorageJanitor.swift`
принимает решение об удалении файла **только** по имени файла и времени модификации, не зная
ничего о `calls.status`. Если агент чинит retry-логику или логику ретеншна — эта развязка
должна быть в голове с самого начала, а не обнаружена через баг-репорт.

## 7. Ссылка на untracked/README.md для структуры вспомогательных материалов

`AGENT.md` уже упоминает `untracked/`, но не поясняет, что там есть собственный `README.md`
с индексом (`untracked/epics/<тема>/README.md` и т.д., согласно глобальным инструкциям
пользователя о структуре `untracked/`). Стоит явно сослаться, чтобы агент не создавал
параллельную структуру для черновых скриптов/исследований.
