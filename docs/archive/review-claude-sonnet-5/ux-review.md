# Podushka — обзор UI/UX и предложения

Автор: Claude Sonnet 5 (Claude Code). Read-only обзор: код `App/Views/*.swift` +
`App/DesignSystem.swift` сверен с планами редизайна (`docs/ui-redesign-plan.md`,
`docs/ui-redesign-v2-plan.md`, `docs/summarization-ui-stub-plan.md`) и с описанием UI
в README.md. `docs/ui-review-kimi.md` намеренно не читался, чтобы не подхватить чужие выводы —
если хотите, могу отдельно сравнить наши два ревью.

Хорошая новость сразу: гипотеза "редизайн наполовину применён, отсюда визуальная
несогласованность" не подтвердилась — оба плана редизайна (v1 и v2) реализованы практически
по всем пунктам, код это подтверждает (ленивый список транскриптов, дорожки по спикерам,
сопоставление с календарём, поправленные тулбар/traffic lights). Основные проблемы UX сейчас —
не "недоделанный дизайн", а конкретные дыры в функциональности и обратной связи.

## Топ находок

### 1. [HIGH] "Показать в Finder" для звонка реализовано, но никуда не подключено
`App/AppController.swift:580` (`revealCall`) вызывает `activateFileViewerSelecting` для папки
конкретного звонка — но ни один View его не вызывает: ни кнопки, ни пункта контекстного меню.
`CallInfo` (`App/Views/CallDetailView.swift:603-621`) просто печатает путь как выделяемый
моноширинный текст. Настройки → Хранение → «Показать» открывает только корневую папку всех
звонков. Пользователю, которому нужен конкретный файл, приходится вручную идти по
скопированному пути в Finder. Уже написанная функция простаивает — это buchstäblich одна
строчка UI-кода, чтобы её включить.

### 2. [HIGH] Нет способа удалить одну запись из интерфейса
`CallStore.deleteCall` сейчас срабатывает только автоматически для тихо отброшенных коротких/
пустых записей (`App/AppController.swift:1485-1488`). Нет ни контекстного меню, ни свайпа, ни
кнопки, чтобы убрать звонок, который пользователь не хочет хранить. Для персонального
рекордера звонков, потенциально фиксирующего чувствительные разговоры, отсутствие пути "я хочу,
чтобы этого не было" (кроме ручной операции в Finder, которую к тому же не найти — см. находку
1) — это не просто неудобство, а лёгкий privacy-риск.

### 3. [MED-HIGH] Мок-саммаризатор неотличим от настоящего
Согласно `docs/summarization-ui-stub-plan.md`, вкладка «Саммари» до сих пор подключена к
`MockSummarizationProvider`, который возвращает один и тот же типовой текст на русском вне
зависимости от реального звонка. В `CallSummaryView.swift` нет ни водяного знака, ни пометки
"демо-данные" — реальный пользователь (например, член семьи, который просто пользуется
приложением), нажав «Сделать саммари», получает выдуманный текст без единого визуального
сигнала, что это не настоящее содержание разговора. Это самый большой разрыв между
документацией и тем, что реально видит пользователь сегодня.

### 4. [MED] В DesignSystem нет типографической шкалы
`Metrics` в `App/DesignSystem.swift` хранит только геометрию (радиусы, ширина сайдбара). Все
150+ объявлений шрифтов по 9 View — это сырые литералы `.font(.system(size: N))`, причём
близкие по смыслу размеры расходятся между файлами (11 / 11.5 / 12 / 12.5 для "второстепенного
пояснительного текста"). Пока ничего не сломано, но любая будущая правка типографики или
проход по accessibility ("крупный текст") не имеет точки опоры — план редизайна ставил цель
"никаких хардкодов вне DesignSystem" (`docs/ui-redesign-plan.md:25`), но она была реализована
только для цвета, не для шрифта.

### 5. [LOW-MED] Точечные хардкоды теней мимо Palette
`PodushkaControls.swift:81,112,250` и `SettingsWindow.swift:692` используют `.black.opacity(...)`
напрямую вместо токена `Palette`. Визуально безобидно, но та же категория дрейфа, которую план
редизайна старался устранить для цветов.

### 6. [LOW-MED] Нет поддержки Dynamic Type (доступность)
Весь текст задан фиксированными размерами в пунктах, а не семантическими стилями `Font` —
системная настройка macOS "крупный текст" нигде в приложении не работает.

### 7. [LOW] Несогласованность формулировок об ошибке
Два почти идентичных баннера ошибки используют разные глаголы для "это не получилось":
"Расшифровка не собралась" (`CallDetailView.swift:381`) против "Саммари не получилось"
(`CallSummaryView.swift:116`). Мелочь, но общий речевой паттерн читался бы как единый голос.

### [Хорошо сделано] Обработка отказа в разрешениях в онбординге
И отказ в доступе к микрофону, и отказ в system audio tap корректно открывают нужную панель
Системных настроек (`App/PermissionChecks.swift:62,96`) — здесь править нечего.

## Пересечение с архитектурным ревью

Находка 2 здесь ("нет удаления звонка") и находка про `CallRecordingPolicy` из архитектурного
обзора (ручная остановка не блокирует авто-рестарт того же звонка) — это по сути одна и та же
тема с двух сторон: у пользователя сейчас недостаточно контроля над тем, что записывается и
что хранится, для инструмента, который по умолчанию слушает звонки. Стоит решать их вместе:
если чинить авто-рестарт после ручной остановки, заодно имеет смысл дать пользователю и явное
"забыть этот звонок" в UI.

## Идеи новых фич/улучшений (для личного инструмента, не enterprise SaaS)

- Пункт контекстного меню/кнопка на карточке звонка: «Показать в Finder» (подключить уже
  готовый `revealCall`) и «Удалить запись» (с подтверждением, подключить `deleteCall`).
- Заметный бейдж "демо-данные" на вкладке саммари, пока `MockSummarizationProvider` не заменён
  реальной локальной моделью — до этого момента отсутствие пометки вводит в заблуждение.
- Быстрый глобальный поиск по всем транскриптам прямо из поповера в менюбаре, не открывая
  главное окно.
- Лёгкий флаг "не записывать это приложение/контакт" на уровне отдельного приложения или
  контакта — сейчас авто-детект пишет всё, что попало под allowlist, без точечных исключений.
- Экспорт одного звонка (аудио + транскрипт) как zip/share sheet — чтобы передать запись
  кому-то без ручного копания в Finder.
