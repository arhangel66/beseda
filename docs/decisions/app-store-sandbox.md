# App Store sandbox audit

## Scope and evidence

The direct and Store variants are distinct build modes, not two proven distribution channels. `BESEDA_STORE=1`
selects a Sparkle-free SwiftPM manifest and Store-only runtime branches; the direct build retains Sparkle,
its update path and its existing entitlements. [Build and release](../architecture/build-release.md#private-store-artifact-beseda-257)
describes the assembly. BESEDA-288 built both modes and statically verified a **full** private ad-hoc
Store bundle, not merely a helper stub. No app was installed or launched, no capture or sandbox runtime
was exercised, and no provisioned signing, TestFlight or App Review was performed.[^verification]

## Public tap feasibility evidence (2026-09-28)

Apple's [Core Audio tap sample](https://developer.apple.com/documentation/coreaudio/capturing-system-audio-with-core-audio-taps) creates a `CATapDescription`, passes it to `AudioHardwareCreateProcessTap`, and uses an aggregate device as the tap's input. It requires macOS 14.2+, `NSAudioCaptureUsageDescription`, and says the system prompts for **system audio recording** permission when recording first starts from the aggregate device. The [usage-key documentation](https://developer.apple.com/documentation/bundleresources/information-property-list/nsaudiocaptureusagedescription) describes the key as an explanation for system-audio capture, not a grant. [ScreenCaptureKit's screen-content guide](https://developer.apple.com/documentation/screencapturekit/capturing-screen-content-in-macos) describes a different capture API; Screen & System Audio Recording permission is not microphone permission. Apple's [audio-input entitlement](https://developer.apple.com/documentation/bundleresources/entitlements/com.apple.security.device.audio-input) describes built-in microphone recording and Core Audio input; it does not explicitly guarantee sandbox access to process taps. The [App Sandbox entitlement](https://developer.apple.com/documentation/bundleresources/entitlements/com.apple.security.app-sandbox) enables containment, not capture authorization. A TCC grant, sandbox capability, usage string, and a correctly provisioned signature are separate conditions. None of these pages promises that a provisioned sandboxed Store app can run this particular tap path. [App Review guidelines §2.5.2](https://developer.apple.com/app-store/review/guidelines/#performance) restrict downloading/executing feature-changing code; they do not certify taps or grant a capture entitlement. No App Review outcome follows from a sample or another listing.

Mac App Store listings indicate Store distribution, hence a sandbox expectation, but do **not** expose a signed binary, its entitlements, its capture API, or actual runtime behavior. ### Separate TapProbe feasibility boundary (source audit only)

`app.beseda.TapProbe` is a distinct bundle ID: standard per-app sandbox containers and `.standard` defaults should have a different domain from `app.beseda.Beseda`. That distinction alone is **not enough** if the probe reuses Beseda code: `AppPaths.current` appends a fixed `Beseda` to user-domain Application Support and `LegacyDataMigration` looks for sibling `Podushka`; `AppSettings` explicitly imports the fixed `app.podushka.Podushka` defaults suite. `Keychain.app` normally derives `app.beseda.TapProbe.keys` and legacy `app.beseda.TapProbe` from the running ID, but its nil-ID fallback is `app.beseda.Beseda`; the owner's login Keychain is shared in the same user. The current `IsolatedCopy` guard treats TapProbe as isolated and **skips process-tap creation and permission-capable calls**, so repackaging Beseda under that ID does not test feasibility. No TapProbe implementation exists in the inspected source tree; its runtime safety cannot be asserted from the name alone.

For a future separate probe, statically verify its actual bundle ID, signed entitlements and code paths before any launch: it must not instantiate `AppController`, `AppPaths`, `AppSettings` or Beseda `Keychain`, import old defaults, use a fixed Beseda/Podushka Application Support path or service, resolve a shared export bookmark, or write into any owner Beseda directory. Use a probe-owned container, defaults and no Keychain access; check every hard-coded path/service and all dependencies, not just the plist. If any shared path, legacy import, same-ID fallback, or unknown access remains, **STOP**; do not run it. This proof only answers process-tap feasibility, not the later exact-ID Beseda sandbox runtime gate. No probe/app was launched or inspected against live data here.

### Signing preflight decision (BESEDA-347; source-only)

**No proven no-dialog route for the existing login-keychain Apple Development key. BESEDA-340 cannot resume unsupervised.** Apple's [`codesign(1)`](https://www.manpagez.com/man/1/codesign/) documents `--keychain` as an identity *search* restriction, not an authorization or UI-suppression switch. Apple's [`security(1)`](https://www.manpagez.com/man/1/security/) distinguishes `find-identity` (locate certificate and private key) from `set-key-partition-list` (change the key ACL, requiring the keychain password; `apple:` allows codesign). Neither identity enumeration nor an unlocked keychain establishes that this process is authorized to use the private key. Security framework's [`kSecUseAuthenticationUIFail`](https://developer.apple.com/documentation/security/ksecuseauthenticationuifail) and [`kSecUseAuthenticationContext`](https://developer.apple.com/documentation/security/ksecuseauthenticationcontext) apply to Security item queries made by a caller; there is no documented `codesign` option forwarding a no-UI item-query policy to its private-key operation. A custom Security-framework probe would not prove the separate `codesign` invocation's authorization behavior. Do not mutate ACLs, partition lists, keys, search lists or export credentials to force access.

The [kit's macOS guidance](https://github.com/arhangel66/ios-kit/blob/main/docs/macos.md) says isolated defaults homes still share the login Keychain and a denied access can leave SecurityAgent on the owner's screen. [BESEDA-196 and BESEDA-224](../architecture/build-release.md#controlled-developer-id-signing-check) successfully signed **Developer ID** throwaways without observed prompts; that is evidence about those invocations and that key's then-current authorization, not a guarantee for the distinct Apple Development key. A 120-second timeout only bounds the CLI process; it does not guarantee dismissal of an independently presented SecurityAgent dialog. `open -g -j`, `CFFIXED_USER_HOME`, and a throwaway file do not isolate the login-keychain authorization UI. A failed or successful ad-hoc sign never exercises this private key.

**Next step:** make owner-supervised Apple Development signing the first step of the BESEDA-222 isolated test window, before packaging or launching the provisioned app. With the owner controlling the session, confirm the intended identity/profile and output path, then sign only a disposable non-app file in a disposable directory; the owner handles or cancels any authorization dialog. Abort on any unexpected UI, identity mismatch or failure; remove only the disposable file and directory, and inspect the resulting signature only after successful signing. Do not proceed to the provisioned build until this gate is explicitly approved and observed. This paragraph is a supervised plan, **not** authorization to use the key now; no signing, GUI, prompt or private-key access occurred in this investigation.
