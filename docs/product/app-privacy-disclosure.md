# App Privacy disclosure audit (Store flavor)

**Status: answers blocked.** This is an evidence map, not a completed App Store Connect questionnaire. Apple's [App Privacy Details](https://developer.apple.com/app-store/app-privacy-details/) defines *collection* as transmission off-device with developer or partner access longer than needed to service the request in real time. It requires accounting for integrated third-party code and all collected data types; an optional feature is **not** automatically exempt from disclosure. The narrow optional-disclosure exception requires *all* Apple's listed conditions, including affirmative choice on each submission and a prominently displayed name/account name. Apple's definitions of [data types, purposes, linking and tracking](https://developer.apple.com/app-store/app-privacy-details/) govern final answers. “Optional” below describes use of the feature, not exemption from Apple's questionnaire. Network transport alone does not establish retention or collection; local-only defaults do not establish non-collection.

Sources audited: [Store dependency split](../../Package.swift), [product privacy](privacy.md), [site policy](../../site/privacy.html), and the source paths below. The site and product policies describe behavior, not provider retention contracts. No Store runtime or provider account inspection was performed.

## Public provider evidence (checked 2026-09-28 UTC)

These are published claims, not verification of the account settings, routed endpoint, CDN logs or shipped binary. They narrow, but do not close, Apple's collection test.

- [OpenRouter provider logging policy](https://openrouter.ai/docs/guides/privacy/provider-logging): each provider has its own logging and retention policy. Account settings separately control routing to providers that may train on paid/free prompts; opting out prevents routing to training providers. Per-request data-policy filtering and an account-wide privacy setting exist. **Neither setting is a universal zero-retention promise**: the policy explicitly says it has no routing rule based on provider retention. Beseda's [chat request](../../Sources/Beseda/Summarization/ChatCompletionsProvider.swift) does not set a provider data-policy filter; the owner's account settings and actual routing remain unknown.
- [OpenRouter privacy policy](https://openrouter.ai/privacy), sections “Model Provider Data Practices”, “Aggregated and De-identified Information”, “How We Share and Disclose Your Personal Data”, and “Personal Data Retention”: inputs go to the selected or automatically routed model provider; providers differ on retaining inputs/outputs and training. The policy describes disassociating inputs/outputs from user IDs for analytics/rankings, and says stored inputs may be re-identified with user ID for debugging. It lists service-provider access to personal data and retains personal data as reasonably necessary for business/legal obligations, **without a fixed API prompt retention period here**. Website Google Analytics disclosure does not prove Beseda embeds Google Analytics. Confirm API-specific prompt logging, debugging, deletion and subprocessors directly; do not equate account training opt-out with OpenRouter's own handling.
- [Hugging Face privacy policy](https://huggingface.co/privacy), sections “Information we automatically collect from your use of the Services”, “Data retention” and “Third Party Service Providers”: Hugging Face says it automatically records service use/session (date, location), IP address, cookie and device information; it retains information as necessary for service, legal, security and legitimate interests, not a fixed model-GET log period. It lists hosting/infrastructure subprocessors including AWS, Google Cloud and OVHCloud. This does **not** identify the CDN or logging policy of a particular redirected model download. Beseda's model GETs contain no intentional transcript payload; redirect destinations and request-log linkage/retention need separate evidence.
- Published dependency manifests: pinned [FluidAudio 0.17.4 Package.swift](https://github.com/FluidInference/FluidAudio/blob/21493f8dac5a97e65742e6ff26f42f164c2fda0f/Package.swift) declares no package dependencies and includes a `NemoTextProcessing` binary target hosted on GitHub; Beseda's [Package.swift](../../Package.swift) declares `CTranscribe` as a binary target at the transcribe.cpp v0.2.3 GitHub release. These manifests describe build-time supply, **not runtime telemetry guarantees**; source/binary and Store-runtime verification are still needed. Neither proves Apple crash-sharing behavior.

## Questions to close before selecting nutrition labels

1. Owner: Is any developer-operated server, crash report inbox, support attachment pipeline, SDK telemetry or analytics receiving app data in the exact signed Store bundle? Audit FluidAudio, CTranscribe and bundled helper manifests/runtime behavior. Who can access Apple crash reports, and do they contain call data?
2. OpenRouter/owner: What are this account's paid/free training and data-policy settings, selected endpoints and fallback routes for chat and Decisions? For each routed provider, obtain current retention/training terms. Does OpenRouter retain API prompts or debugging copies beyond real-time service; for how long, with which subprocessors, deletion rules and account/IP linkage? Does any party combine these requests with third-party data for advertising/measurement or broker them?
3. Hugging Face/CDN: For these exact `/resolve/` GETs, which CDN/redirect recipients receive IP, user-agent and request identifiers? What logs persist, for how long and for what purposes? Is an identifier linked to an account or used for tracking?
4. Owner: Which LM Studio remote hosts and webhook endpoints are supported/expected, who controls them, and can the owner accurately attest to their retention and use? Does the webhook payload or any cloud request contain event titles/emails or other contact information beyond transcript text? What purposes apply to each transmission (app functionality versus other uses)?
5. Owner: For each remotely retained type, determine Apple's exact category, purpose, linked-to-user and tracking answers using evidence from providers and the shipped build. Are sensitive/health/financial details possible in recorded conversations and how should Apple classify such free-form content? Does any flow actually satisfy **every** condition for Apple's optional-disclosure exception? Obtain current provider terms and owner sign-off; do not mark “Data Not Collected” based on default local mode.

No answer here claims that remote services track users; absence of evidence is also not a defensible “not tracking” answer. Do not submit a label until these questions are resolved for the shipped Store binary.
